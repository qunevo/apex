# APEX 0.4: declarative scheduling acceptance report

24 September 2026. Synthetic data only. This report separates implementation evidence, comparable-model measurements and the cost of additional rules. It does **not** certify universal non-regression, complete private v2 parity or production readiness.

## Result

- **24/24 fixed-evaluation groups preserve quality**, with identical assignments and metrics in all 144 measured pairs.
- **24/24 fixed-evaluation groups pass the stated 5% paired-median runtime margin**; end-to-end CLI wall time also passes in 24/24 groups. This is a noise-tolerant engineering gate, not proof of exact equality or a statistical non-inferiority certification.
- **8/8 equal-time-budget groups preserve or improve the actual objective**. **1 group fails the runtime margin** because evaluation-boundary stopping permits an overrun; see details below.
- **97 Rust tests pass**, up from 74. Formatting, Clippy with warnings denied, release build, official MCP SDK tests, HTTP tests and browser workflows pass.
- Maintenance is improved structurally: one mandatory filter stage serves all strategies, both searches and forced prefixes; template lowering reuses existing constraints and objective evaluators. The change-locality examples below demonstrate this, but do not measure future maintenance effort.
- The complete acceptance demand “every model is at least as good and at least as fast” is **not established**. Active exact policies have additional costs, changed restrictions can worsen goals, and Q quality depends on the scheduling structure.

## What is implemented

The [versioned planning vocabulary](../architecture/declarative-scheduling.md) has selectors, resource eligibility, windows, resource sequences, campaign/idle-gap/urgency policies and weighted completion goals. The existing physical model retains calendars, running work, fixed decisions, conditional DAGs, routes, material flows and other supported relationships. `apex.v3.4` accepts canonical v3.1–v3.3 input.

Fast Planner, Trainer and Plus share `dispatch.rs`. Forced decisions are filtered too; Plus obtains next choices without requiring a successful greedy suffix. Active policies inspect the complete eligible ready pool, so candidate 65 cannot disappear behind the Q window. Q normalization follows filtering.

Exact placement uses the existing calendar primitive for a capability-checked independent-task subset, and full prospective-prefix decoding otherwise. The latter accounts for predecessor post-work; terminal cleanup is deferred. Arbitrary native sequence logic must declare and test prefix-safe semantics before receiving exact facts. Full reconstruction remains expensive; general rollback/indexed witness queries are future work.

Governed schedules carry model/extension fingerprints, complete chosen decisions and bounded reasons. Validation separately checks physical assignments and replays the policy witness, including explanations and counters. These are construction-policy semantics, not arbitrary final-schedule mathematical invariants.

In the failed 256-task declarative Trainer group, 0.4 completed six evaluations; 0.3 usually stopped after five. The score and assignments were identical. ## Cost of active policies

These rows compare **different work contracts**. “None” has no mandatory policy; “direct” has four campaign policies; “full prefix” adds a deliberately never-matching sequence rule to force the general oracle without changing the chosen plan. Direct and full-prefix results match exactly in every measured 16/64-task method pair. Six evaluations and population 4 are used for searches. Three measured repetitions follow a warmup.

The full ready-pool scan and general prefix reconstruction do not yet scale like the old bounded Q window. Full decoding is limited to 100,000 probes per construction/replay; exceeding it returns a budget diagnostic. Large imports do not imply that a 100,000-task model with dynamic policies has been scheduled within an interactive latency target. Sparse ready sets and independent-resource models behave differently from wide coupled pools.

An explicit two-task counterexample is also retained: an initial A campaign delays an urgent B task. Weighted tardiness rises from 0 to 100 seconds when the declared campaign is activated. This is a changed admissible decision set, and demonstrates why adding hard filters cannot promise never to worsen every metric.

## Goal-to-Q evidence

The new weighted completion template reuses the existing coefficient/work proxy. For each of 12 synthetic six-task cases, all 720 permutations were evaluated analytically; the selected Rust plan’s metric was checked against that independent evaluator. Six simple available-work cases form the restricted case set; six additional cases introduce release times. The order surrogate is the sum of position times coefficient/work; its rank correlation with actual weighted completion is reported, rather than claimed to be the final objective.

## Semantics and maintenance evidence

| Evidence | Result |
| --- | --- |
| Existing Rust tests | All original 74 pass |
| New dispatch and tool tests | 23 additional tests pass; 97 total, one unrelated opt-in report test remains ignored |
| Scope completeness | A matching task beyond the 64-task Q window is selected |
| Bypass protection | Forced prefixes, singleton pools and custom rejections cannot bypass policies |
| Temporal interactions | Breaks, rates, retained occupancy, predecessor post-work, deferred terminal cleanup, running remainder, materials and receipts tested |
| Relationships and commitments | Route resolution, min/max lags, consecutive order and explicit fixed-start exemptions tested |
| Native integration | Same filter tested in Fast Planner, Trainer and Plus; unsupported exact decoration and invalid rejections fail |
| Search | Prefix expansion can survive a failing greedy suffix; mutations/generations are exercised; serial and parallel Trainer preserve score/order under fixed evaluation budgets |
| Corruption | Missing/foreign witnesses, changed decisions, forged explanations and invalid replay weights rejected |
| Lowering | Declarative and equivalent explicit models produce identical assignments/metrics; generated Q names are valid before lowering |
| UI and transports | 30 tools over both MCP transports; saved-result explanations, derived commitments, rule descriptions and mobile layout tested |
| Large intake | 100,000 tasks imported through bounded chunks; maximum append response 130 bytes; this is an intake test, not a large-policy planning benchmark |

The engine file decreases from 1,068 to 774 lines by moving construction to a named module. Total code increases because policies, probes, witnesses, schema and tests are new functionality. Smaller file size is not itself a maintenance proof.

Concrete change-locality exercises are stronger evidence: a resource restriction, time window and sequence are composed in JSON and lowered to existing verified primitives; a completion metric gets its evaluator/Q without modifying either search; a test-only native filter changes admissible choices in all three methods without algorithm-specific edits. New semantics still require source, tests, versioning and any necessary viewer support. Generalized arbitrary expressions and auto-generated solvers are intentionally absent.

## Agent and viewer workflow

1. Ask the planner for scope, initial history, units and exceptions; inspect `policy.inspect` and `schema.get`.
2. Fork the current scenario and patch its `planning` block. Supported templates need no runtime code generation.
3. Run Fast Planner, Trainer or Plus with explicit budgets; inspect actual KPIs and independent validation.
4. Explain the selected step with `schedule.explain_decision`; compare the saved result against its baseline.
5. For new semantics, implement a versioned Rust extension and its tests, rebuild, then repeat the evidence checks.
