# APEX 0.5: essential scheduling-model additions

24 September 2026. Material preparation now preserves free workplans and reallocates actual supply per selected routing. Upstream job/order urgency affects construction without rewriting business dates. Trainer and Plus can explicitly choose conditional resource modes. Additional task/job/order, resource and stage KPIs are independently checked and exposed through paginated tools and a compact viewer.

The requested four areas are implemented with synthetic acceptance coverage. **Full V2 parity, universal quality dominance and equal runtime are not established.** The bounded [current model contract](../data-model.md) includes subsequent changes; the results below describe the 0.5 implementation.

## Observable behavior

| Case | Result |
| --- | --- |
| Prepared producer workplan changes from slow to fast | Material is reallocated to the active producer; no inactive route output or double supply. Split quantities and actual source IDs are retained in the saved report. |
| Initial route lacks material; another route is supplyable | Preview reports the shortage. The bad route fails evaluation; Plus finds the feasible route. No task is silently dropped and no order is invented. |
| Upstream operation due 800 / priority 1 feeds order due 75 / priority 9 | Dispatch urgency becomes 75 / 9; the operation's business due remains 800. Physical edges propagate urgency; resource-order locks do not. |
| Locally faster preparation blocks another resource | Quick construction yields makespan 110 s; Trainer, Plus and combined improvement find the 100 s plan by selecting the 12 s free-resource preparation instead of the 10 s shared-resource preparation. Same forced prefix, 48 evaluations, time disabled. This is a synthetic counterexample to local earliest finish, not a universal search guarantee. |
| Preparation, post-work, restart and transition alternatives | Choices replay; incompatible hard commitments and tampered results are rejected. Main-mode-specific choices exclude incompatible main modes. Conditional branching works at the Plus task-depth boundary. |
| Native compile hook supplies conditional alternatives | Trainer and Plus find the better alternative and independent customized validation/replay succeed. Sequence-hook-only dynamic alternatives remain a separate catalog limitation. |
| Fractional KPI/native objective survives storage | JSON floating-point round trips preserve values; reloaded schedules validate. This fixes an issue detected in the HTTP workflow during implementation. Missing/corrupt version-1 KPIs fail validation. |

The [synthetic chain example](../../examples/chain-routing.json) demonstrates all four feature areas through agent tools. A baseline explicitly using its slow route has makespan **90 s**, order tardiness **15 s** and weighted order tardiness **135 priority-seconds**. Combined improvement on the same free-route model chooses the fast route: **50 s**, **0 s**, **0 priority-seconds**. The final viewer run took about **11.4 ms** for 48 complete evaluations on this tiny case; this is a single feature demonstration, not a representative performance estimate. [Recorded workflow](v0.5-viewer-migration.json).

## Direct legacy evidence

[The new comparison](v0.5-route-material-legacy.json) executes the unmodified V2 `MaterialDispatcher` on two identical-material BOM alternatives, then evaluates both Rust workplans in a single free prepared scenario. Normalizing task IDs to the legacy producer job yields exactly the same source quantities: 2 raw pieces from stock, 1 part to assembly and 1 part to packing from production. Both Rust schedules validate.

This checks material sources/quantities, not identical route-selection heuristics, complete job-adapter behavior or decoder/search equivalence. Earlier selected decoder/material comparisons remain historical evidence. V2's recursively modified due dates and day-based KPI units must not be silently equated with the new separation of business dates, dispatch urgency and second-based metrics.

## Runtime and quality versus Rust 0.4.1

[Raw measurements](v0.5-migration-measurements.json) contain **104 paired comparisons**: five synthetic/production-shaped inputs, four methods, two seeds, two retained repeats, plus 100 ms soft-budget comparisons on the 256-task and production cases. One warmup is excluded and binary order alternates. Fixed evaluation cases use 24 evaluations, one worker and Trainer population 4. Construction timing includes validation; process startup and JSON I/O are additionally recorded as wall time. No other build/test process ran during this final measurement pass.

All **104 pairs matched the previous metric values**, including active objectives. This is evidence on these inputs, not a guarantee for other data. New capabilities are exercised separately because 0.4.1 cannot accept their new fields. No external solver was benchmarked.

Median core milliseconds at equal evaluation budgets, shown as **0.4.1 → 0.5**:

| --- | ---: | ---: | ---: | ---: |
| production | 0.69 → 0.81 | 9.76 → 11.69 | 11.28 → 12.94 | 10.14 → 11.68 |
| shift-factory | 0.68 → 0.76 | 10.40 → 12.15 | 9.75 → 11.74 | 10.20 → 11.82 |
| synthetic-32 | 2.44 → 2.58 | 41.58 → 42.08 | 39.25 → 40.42 | 40.09 → 38.75 |
| synthetic-256 | 54.39 → 52.05 | 814.17 → 839.77 | 868.07 → 901.15 | 806.69 → 829.56 |

The 5% median-overhead engineering margin passes **12 of 20** fixed-evaluation method/input groups. The small shift/production fixtures exceed it, with paired median overhead of approximately **13–21%**. Absolute overhead is roughly 0.09–0.12 ms for their quick plans and 1.5–2.0 ms for their 24-evaluation searches. On 256/1,024 plain tasks, measured search overhead is approximately 2–4%. These measurements **do not satisfy a blanket “at least as fast” claim**.

At 100 ms nominal budgets, returned results also match prior metrics in the tested cases. Actual times can exceed 100 ms because the budget is checked between complete evaluations. Peak process working set across these tests is below 27 MiB, but these are at most 1,024-task planning instances, not a 100,000-operation planning scalability demonstration. Large transport imports remain a separate capability.

## Proxy quality and remaining search limitations

[The proxy diagnostic](v0.5-proxy-measurements.json) evaluates first-choice Q scores against complete-schedule lost job-delivery fraction for all eight forced first choices on 24 synthetic four-job instances. Twelve cases are held out from the initial batch; the mapping was not tuned on either batch. This is a diagnostic of the chosen mapping, not an optimality benchmark.

On the held-out cases, 3 signals are constant; among the other 9, median Spearman correlation is **0.252**, with **2 negative correlations**. The Q-preferred first choice loses to another tested completion in **5 of 12 cases**, by up to **0.25 delivery fraction**. Thus the grouped delivery/count/max-lateness mappings remain explicitly **experimental**. Exact fitness ranks complete schedules; the mapping is not presented as proven or automatically derived from arbitrary mathematics. Utilization and new conditional/total mode-cost metrics remain visibly unmapped to standard Qs.

The Trainer still evolves construction policies, now with conditional modes as additional genes. It does not evolve arbitrary start times or automatically invent Q formulas. Conflicting route/conditional genes can consume failed evaluations. Plus seeds preserve their supplied conditional commitments; the portfolio can explore different seed policies. Native sequence decorations need advance stable declarations before their newly generated conditional alternatives can become genes.

## Verification and maintainability

- `cargo fmt --check`, strict Clippy and the final full `cargo test` pass: **122 tests**. Two measurement tests are opt-in; the new proxy report test was also executed in release mode.
- The new [migration tests](../../tests/migration.rs) cover positive, negative and corrupted-output behavior, route/material interactions, urgency, conditional commitments, restart/transition/mode context, native compilation, parallel Trainer reproducibility, KPI units and JSON persistence. The new [service test](../../tests/service.rs) covers the complete agent workflow and immutable result inspection.
- Official MCP SDK: **6 stdio workflows** and **5 Streamable HTTP workflows** pass. HTTP also exercises authorization/origin checks, native customization, parallel Pareto search, replay and freezing. [Stdio](v0.5-agent-workflows.json), [HTTP](v0.5-http-workflows.json).
- Four browser suites pass: lean viewer, workbench, mandatory-policy viewer and the new migration workflow. The new suite checks actual material links, chain urgency, selected conditional modes, KPI pagination/proxy labels, compact comparison, deep links and 800 px layout. Screenshots were inspected. [New workflow](v0.5-viewer-migration.json), [plan screenshot](v0.5-chain-viewer.png).
- The user's earlier 0.4.1 saved schedule was revalidated successfully after upgrading the local server. This is selected compatibility evidence, not a guarantee for every historical policy witness.
- Planning/intake skills and executable schemas are updated. Both edited skills pass the skill validator.

One existing 1 ms wall-clock deadline test returned `IMPROVE_BUDGET` during a concurrent build and passed in the final isolated full suite. Such tiny real-time assumptions remain load-sensitive; they are not used as performance gates above.

The implementation consolidates urgency in `urgency.rs`, conditional-choice semantics in `conditionals.rs`, KPI definitions in `metrics.rs`, and allocation in `material.rs`. The same decode/validation paths are used by quick construction, Trainer and Plus; there is no separate relaxed implementation per search mode. This structure and focused regression coverage support maintainability, but do not constitute a quantitative maintainability proof.

## Open migration boundaries

Differing-material **main modes** still require selection before pegging; the allocation policy itself is not optimized globally. Chain urgency does not yet subtract exact downstream calendars/lag. Legacy slack distributions, every stage penalty/statistical aggregate and customer-specific KPI formula are not all migrated. Historical day-based/due-recursive metrics require explicit semantic mapping. Direct-schedule GA/bandit operators, automatic Q formula generation and generated operators remain the documented **GA-01, QGEN-01 and OPGEN-01** items in [the development backlog](../architecture/combined-improvement.md). No MRP, solver backend, general stochastic simulation or unrestricted activity graph is added by this release.

## Reproduction

```text
cargo fmt --check
cargo clippy --all-targets -- -D warnings
cargo test
cargo build --release
cargo test --release --test migration_report -- --ignored
python scripts/benchmark_migration.py --baseline .apex/v2-completion-baseline/apex.exe --candidate .apex/v0.5-measured/apex.exe
npm run test:mcp
npm run test:http
node tests/viewer-migration.mjs
node tests/viewer-plan-smoke.mjs
node tests/viewer-dispatch-smoke.mjs
npm run test:viewer
.apex/legacy-runtime/Scripts/python.exe scripts/compare_route_material.py
```

The browser scripts require the local viewer. The recorded legacy comparisons used an isolated runtime and source that have since been [removed with their comparison scripts](legacy-baseline.md); those comparisons are historical evidence. `APEX_BINARY`/`APEX_VIEWER` can point transport/browser tests at another built executable/server.
