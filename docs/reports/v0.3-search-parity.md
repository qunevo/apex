# 0.3 search, parity and workbench verification

23 September 2026. Rust release build on this Windows x86-64 development machine. Fixtures are synthetic. This report describes measured behavior, not optimality, production readiness or unrestricted equivalence with every legacy pipeline/customization.

## Implemented in this revision

- Evolutionary trainer with per-stage Q genomes, mutation, stage-block crossover, unpinned route genes, elitism, generation/evaluation/time limits and parallel evaluation.
- Weighted priority objectives with min/max directions and explicit scales; optional Pareto fronts/crowding and a bounded, replayable nondominated archive.
- Fast Planner Plus with stored decision prefixes, UCT selection, complete randomized rollouts, alternative branches and revisits. Prefixes are reconstructed, not incrementally decoded.
- Nineteen standard Qs, automatic attribute-completion proxies, native evaluator/proxy declarations, mapping inspection and explicit missing-proxy reporting.
- Freeze shading, T/R/M/S/B and running markers, fixed-sequence connectors and commitment details; UI controls for workers, budgets, objectives, Pareto candidates and Plus.
- The same 27 tools over MCP stdio, Streamable HTTP and plain JSON/OpenAPI. `queues.inspect` and `schedule.plus` are new. Options schemas come from Rust types rather than a separately maintained field list.

The [search contract](../search-and-parity.md) answers the exact limit, objective, Q aggregation, genotype, crossover, mutation and parallelization questions.

## Actual v2 execution comparison

The generic v2 Python pipeline was run with its existing CPython 3.11 Cython decoder in an isolated legacy environment. No legacy source was edited. The fixture harness translates only its deliberately synthetic cases, carries full alternative choices into Rust, then pins the selected legacy route/mode/order decisions to compare decoding semantics. It is **not** a general legacy importer and does not compare stochastic optimizer trajectories.

| Case | Evidence |
| --- | --- |
| Quantities, mode alternatives and technological precedence | Same four active operations and exact main-work intervals; makespan 1,140 s |
| Resumable calendar break | Exact intervals in both engines; makespan 1,440 s |
| Main-mode pre-work and predecessor post-work supplied through a sequence matrix | Exact main-work intervals; makespan 1,220 s |
| Reversed consecutive sequence on a fixed resource | Exact intervals; makespan 1,365 s |
| Alternative whole workplan with different active operation presence | Same two active operations; makespan 390 s |
| Shift productivity changes from 0.5 to 1.0 | Deliberate correction: Rust completes 300 work at t=375; legacy reports t=300 |

The rate difference is explained by `get_stretched_duration_by_productivity` in `src/v2/cython/fastdecoder/fastdecoder.pyx`: its overflow branch calculates the remaining slot from the already clipped bar end. In this case that slot becomes zero and undercounts elapsed work. Rust integrates `150*0.5 + 225*1 = 300`, and its independent validator verifies the work. Replicating the legacy interval would violate the specified productivity.

Another mapping finding: v2 creates conditionals with zero work and fills their duration from sequence effects. Copying only `conditionalOperations.processingTimeSeconds` into fixed Rust work would change semantics. The harness now translates the actual sequence effects, including the absence of terminal post-work. Rust can separately express explicit terminal cleanup.

These comparisons were produced by the former `scripts/compare_legacy.py` using an isolated legacy runtime. The v2 source and comparison harness have since been [removed](legacy-baseline.md), so this checkout cannot rerun the legacy side. [Exact interval evidence and the reviewed rate correction](v0.3-legacy-comparison.json) are retained. At the time of the comparison, the 161 source hashes from the previous baseline were checked unchanged.

## Runtime and search quality

Release measurements use 24 complete evaluations, no time cap, three repetitions and the median. Both worker configurations use the same trainer seed/population/evaluation count. Times include construction, decoding and independent validation; API serialization is excluded. Plus additionally reconstructs prefixes. Measurements are workload examples, not a throughput SLA.

| Dataset | Fast Q planner | Trainer, 1 worker | Trainer, 4 workers | Plus, 1 worker | Plus, 4 workers |
| --- | ---: | ---: | ---: | ---: | ---: |
| 100 synthetic operations | 11.87 ms | 242.61 ms | 93.78 ms | 348.78 ms | 188.85 ms |
| 1,000 synthetic operations | 161.72 ms | 3,361.80 ms | 1,190.17 ms | 4,811.90 ms | 2,543.87 ms |
| Production example: five lots, alternative routes, ten active operations, conditionals | 0.34 ms | 8.60 ms | 4.62 ms | 9.55 ms | 5.76 ms |

At 1,000 operations the trainer is approximately **2.82×** faster with four workers; Plus approximately **1.89×**. Parallelization is useful. Prefix reconstruction limits Plus scaling, and tiny inputs may be dominated by thread overhead. This Q planner evaluates more candidate signals than the old due-date-only fast path, so old 0.2 throughput numbers must not be presented as equivalent current Q timings. Classic `strategy: "due"` remains available when that trade-off is desired.

On the production example, the 24-evaluation trainer reduces order weighted tardiness from **1,865 to 490** and makespan from **3,095 to 2,945 s**. Plus reduces tardiness to 1,765 but increases makespan to 3,290 s; that is valid under tardiness-first priorities. On the 1,000-operation example, Plus finds no improvement within 24 evaluations. Search is not a guarantee of improvement, and an unchanged best candidate is retained.

[Raw timings, settings and quality measurements](v0.3-search-measurements.json), generated by [the opt-in release test](../../tests/search_report.rs).

## Proxy correlation: measured rather than assumed

For each of 40 varied synthetic 12-task instances, every eligible first task/mode choice was forced, the remaining schedule completed, and its actual weighted tardiness compared with the first-choice Q cost. The first 20 instances diagnosed the original mapping; the next 20 were held out until the revised mapping was evaluated. Spearman correlation uses average ranks for ties; lower Q cost and lower tardiness should correlate positively. This is a first-decision diagnostic, not an end-to-end optimality test.

| Mapping / partition | Mean Spearman | Negative cases | Mean regret versus best tested first choice |
| --- | ---: | ---: | ---: |
| Initial due/slack/priority mapping, initial 20 cases | 0.108 | 5/20 | 3,735.4 weighted seconds |
| Work-aware urgency mapping, same 20 cases | 0.261 | 1/20 | 479.15 weighted seconds |
| Revised mapping, 20 held-out cases | 0.192 | 3/20 | 375.95 weighted seconds |

The revision adds apparent tardiness and stops treating an implicit horizon as a differing hard deadline. Automatic attribute completion uses urgency per estimated work; pairwise single-machine tests verify its objective ordering. The revised generic proxy improves this diagnostic substantially, but correlation remains modest and counterexamples remain. **There is no universal correlation guarantee for these Qs or for arbitrary new metrics.** Full validated objectives, elitism and retained alternatives are the safeguard. New custom objectives require representative quality tests and a separate holdout before their proxies become defaults.

The [initial measurement artifact](v0.3-search-initial-measurements.json) is preserved, including its poor results. Negative correlations remain explicit warnings in the measurement output.

## Parity acceptance boundary

The tested core covers breaks, rate changes, interruption/retention semantics, pre/post DAGs, neighboring sequence effects, alternatives, quantities, temporal materials, running remainders/restart work, independent fixation dimensions, noninterleaving blocks, job/order completion and native decoration/evaluation/validation. Search mechanisms missing from 0.2 are now implemented and tested; they are not merely renamed portfolio strategies.

This is still **not an unrestricted full-system v2 parity certificate**. Automatic BOM explosion, supply pegging and legacy-specific preprocessing policies are not implemented as a generic adapter. The complete legacy KPI catalog, units and private callbacks are not automatically reproduced: for example, Rust `on_time_delivery` is a due-dated task count, whereas v2 reports a job fraction. New native goals require explicit evaluators and proxy contracts. Unrestricted cross-task internal event graphs, arbitrary preemption, named-worker substitution mid-phase, simultaneous batch formation and stochastic simulation remain outside the current contract; their absence must not be mistaken for evidence that all were working legacy features.

The legacy source was later removed at the user's request; retain the [historical audit](v2-parity-audit.md) and recorded comparison evidence. Removal does not certify the outstanding production-specific migration cases. This report did not publish the repository or complete the separate publication-cleanup process.
