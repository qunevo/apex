# APEX 0.6: direct GA and remaining special cases

24 September 2026. Synthetic data only. The direct GA is implemented, linked to `schedule.improve`, exposed through the existing agent tools and visible in the read-oriented viewer. It is not a full migration certificate for every legacy extension.

## Delivered behavior

The implemented experimental sequence is Trainer → Plus → direct schedule GA with 40% / approximately 30% / 30% of the **same** overall allowance. The **released default remains Trainer/Plus (40%/60%)**, because the fixed GA reserve failed the non-regression quality criterion. Agents enable the third phase with `options.improve.evolution_share = 0.3`, or explicitly refine a saved plan via `schedule.evolve` (or the diagnostic CLI). The normal planner still asks for a quick plan or an improved plan. The direct GA evolves operation priorities, execution modes, whole workplans and conditional-resource modes, rather than only Q weights. Its population uses elitism and optional Pareto selection; the retained displayed winner follows the configured objective priorities.

Ten versioned operators include operation insertion/swap, job/resource blocks, a lateness-guided move, main-mode/workplan/conditional changes, conditional-choice reset and actual job-order crossover. Uniform and discounted-UCB selection are available. One operator produces each candidate, so credit attribution is explicit. Native mutation/crossover proposals are extensible through the linked customization trait. The core checks chromosomes, protects commitments, decodes and independently validates candidates. No generated source code is executed by runtime tools.

The implementation deliberately retains the constructive decoder. A priority permutation is repaired by the ready set and mandatory policies; it cannot express every arbitrary start-time schedule. The best observed valid incumbent survives the entire run. This does not guarantee equality with a different algorithm spending the full budget.

See [the detailed contract](../direct-schedule-evolution.md), [implementation](../../src/rust/evolution.rs) and [semantic tests](../../tests/evolution.rs).

## Special-case audit

| Area | 0.6 result and evidence | Remaining boundary |
|---|---|---|
| Main modes with different material requirements | Preparation preserves the alternatives. Each candidate chooses a mode and redoes pegging; Trainer, Plus and GA recover from a synthetic shortage in the shortest mode. Actual allocation reports and corrupted quantities are revalidated. | Supply pegging order is a fixed policy, not a globally optimized allocation chromosome; no MRP. |
| Whole-workplan/BOM interactions | Rich fixtures and existing migration tests retain active routes, dependencies, stock and producer/consumer relationships through GA and replay. | No claim of exhaustive legacy preprocessing equivalence or of finding every feasible allocation. |
| Native sequence-created conditional alternatives | New advance declaration hook makes stable activity/mode IDs searchable in all three searches. The test moves preparation to an independent resource and reduces makespan from 110 to 100 seconds. Missing or corrupted selected activities fail. | Prefix branching requires a valid prefix-decoration contract; undeclared new activity identities are not automatically invented as genes. |
| Frozen starts, resource/mode/order commitments, breaks and maximum lags | Dedicated GA tests combine fixed starts, consecutive sequences, resumable breaks, maximum lags and explicit mode choices; every returned plan validates and replays. | Tight maximum lags can still cause a constructive failure even if another feasible schedule exists. |
| Running work and restart resources | Actual work is preserved byte-for-byte in the semantic test; a fixed restart alternative and caller-pinned main mode survive evolution. | General interruption decisions and arbitrary preemption remain outside the model. |
| Mandatory dispatch rules | Direct priorities still use the complete eligible pool. A required family continuation beyond the 64-candidate Q window is found. All new candidates pass shared filters and policy witness validation. | Existing exact-placement/prefix cost and policy semantics remain unchanged. |
| Native genetic operators | A malformed operator is rejected and charged, receives zero reward, and cannot replace valid incumbents. Serial/4-worker GA results and reward attribution match at a fixed evaluation budget. | Dedicated bottleneck/setup-specific operators, online source generation and adaptive phase allocation remain future work. |
| Persisted decisions | New construction records distinguish actual decode order from input-ordered assignments. Altered main-mode commitments or construction metadata fail validation. The previous user-visible 0.5 schedule was also revalidated after upgrade. | Old schedules without construction records remain readable; their GA priority seed uses start order while preserving the original incumbent. |
| Chain urgency / slack | Existing due-date and priority propagation remains active, including actual material edges. Legacy `Task.get_real_slack_time` and KPI extraction were reviewed again. | Exact downstream calendar/lag-adjusted slack is **not** implemented. Legacy slack uses recursively accumulated nominal duration and asymmetric priority weighting; it is not simply `due - ready`. |
| Remaining legacy KPIs | Existing grouped delivery, resource utilization, conditional time/cost and stage KPIs remain independently checked. | Legacy slack aggregates, every stage penalty/statistical aggregate and private formulas are not all ported. The old negative-slack-by-stage loop also indexes `task.stage` where `stage` is intended; reproducing that apparent defect is not a parity goal. |

The legacy GA references were the generic discounted-UCB mutation portfolio and job/topological crossover in `src/v2/scheduler/deepsearch`. The Rust implementation is a redesigned equivalent capability, not a claim of identical random trajectories, annealing or objective scaling. Q formula generation (QGEN-01) and automatic operator generation (OPGEN-01) remain open. GA-01's direct-search baseline is now implemented.

## Equal-budget results and release decision

[Raw reproducible measurements](v0.6-evolution-measurements.json) contain **552 search runs** plus **40 quick-plan runs (20 pairs)**. All returned saved results pass independent validation. Fixed-budget searches use 64 total candidate evaluations, population 8, one worker, four seeds and two measured repeats after warmup. Nine models include the existing shift/material/campaign examples, 32/256-operation synthetic inputs and two previously unused dependency/release-time variants. No tuning used the held-out results.

The following table reports **36 distinct model/seed combinations**; repeated timing runs are not counted as additional quality evidence. Comparisons use the complete lexicographic score against the retained 0.5 Trainer/Plus binary.

| 64-evaluation variant | Better | Equal | Worse | Median paired runtime / 0.5 |
|---|---:|---:|---:|---:|
| Released 0.6 default: Trainer/Plus | 0 | 36 | 0 | 1.007 |
| Experimental Trainer/Plus/GA, 30% GA reserve | 2 | 26 | 8 | 0.956 |
| Same reserve, uniform operator selection | 1 | 27 | 8 | 0.965 |
| Quick initialization + direct GA | 5 | 11 | 20 | 0.704 |
| Trainer (32) + GA (32) | 5 | 20 | 11 | 0.914 |
| Plus (32) + GA (32) | 7 | 11 | 18 | 1.002 |

**The fixed GA reserve fails the non-regression quality gate.** It is implemented but not promoted as the default. The GA improves the preceding phase in 3 of 36 combinations, while giving up Plus budget causes more losses overall. Its neighborhood can help a given plan without being the best use of a short total budget. UCB beats uniform selection in 3 combinations, ties in 32 and loses in 1; this is insufficient evidence of general superiority.

The released default matches the 0.5 objective score in all 36 fixed-budget combinations. Its overall paired runtime median is about 0.7% higher. This is empirical non-regression on the tested set, **not** an equality proof for all instances or machines. The small release-time fixture has approximately 7% overhead (about 0.4 ms per 64-evaluation search), so even the retained standard allocation does not meet a universal speed claim.

Under a nominal **100 ms** allowance, 16 repeated comparisons on two models show the optional GA reserve better 3 times, equal 11 times and worse twice than 0.5. The released default is better twice and equal 14 times in those measurements; timing-dependent evaluation counts differ. The largest measured soft-deadline completion is 137.6 ms. Budgets are checked between evaluations/batches, not enforced through preemption.

Quick planning retains **identical KPI values in all 20 pairs**, including a 1,024-operation case. The median paired runtime ratio is approximately 1.000. Individual small cases vary: the release-time fixture is about 0.42 vs 0.38 ms, and 1,024 operations about 186 vs 183 ms. These are selected runtime/quality measurements, not a 100,000-operation planning demonstration. Measured search peak working set is at most about 20.2 MiB on the tested inputs of at most 256 operations.

The two-stage diagnostic combinations include their seed search, seed validation/handoff and GA in the reported timing and total 64 evaluations. For a later `schedule.evolve` call, retaining a supplied plan proves that call cannot worsen its incumbent; the earlier planning cost and the new budget must still be reported separately. Distinct chromosomes provide structural diversity only. Better operator applicability, targeted neighborhoods and evidence-based budget allocation remain sensible next steps; no further default was tuned to these benchmark cases.

## Reproduction

```text
cargo fmt --check
cargo clippy --all-targets -- -D warnings
cargo test
cargo build --release
python scripts/benchmark_evolution.py --candidate target/release/apex.exe
npm run test:mcp
npm run test:http
node tests/viewer-evolution.mjs
node tests/viewer-migration.mjs
node tests/viewer-plan-smoke.mjs
node tests/viewer-dispatch-smoke.mjs
npm run test:viewer
```

The benchmark expects the retained local 0.5 executable at `.apex/ga-baseline/apex.exe`. It compares old/new and shortened pipelines on identical synthetic models and budgets, records invalid outputs and negative results, and validates every saved benchmark plan. Browser tests require the local viewer; Windows tests default to installed Edge. Runtime binaries, local stores and benchmark intermediate schedules remain in ignored `.apex`/`target` paths.
