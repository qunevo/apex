# Repository conventions

- Use English for source comments, identifiers, documentation, examples and user-facing messages in the repository. Conversation language can follow the user.
- Keep the scheduling core independent of any real customer. Place optional source adapters and domain extensions in customization modules.
- Commit only deliberately synthetic examples. Do not copy or rename customer exports into fixtures. Do not commit customer names, identifiers, production data, credentials, private endpoints, model checkpoints or derived vector stores.
- Read credentials and deployment-specific values from the environment. Keep `.env` files and generated outputs out of version control.
- Follow the root `LICENSE` (APEX Source Available License 1.1), `LICENSING.md` and the matching summary in `docs/legal/pricing.md`. The root license is the canonical public grant; separate commercial and contributor agreements require express acceptance and are not supplied as unfinished repository templates. Do not invent different thresholds or prices, add a permissive license, claim OSI open-source status or introduce per-operation, per-user or per-run metering.
- Clearly distinguish the runnable Rust implementation from the historical v2 migration audit, proposed architecture and the draft v3 data model. The v2 source and its execution harnesses have been removed.
- The runnable Rust implementation is in `src/rust`, with executable schema `apex.v3.4` and canonical `apex.v3.1`/`apex.v3.2`/`apex.v3.3` input compatibility. Do not confuse it with the earlier `3.0-draft.1` design example. See `docs/implementation.md` and `docs/data-model.md` plus `docs/architecture/declarative-scheduling.md` for current capability limits.
- For a scheduling rule or objective change, update typed input, readiness checks, evaluation, objective/heuristic semantics and independent validation together. Add semantic, negative and corrupted-output tests; never disable hard rules to improve a score.
- Run `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings` and `cargo test` for Rust changes. Rebuild the release binary before MCP/browser verification. Report measured results separately from design goals and optimality claims.
- Keep `.apex` artifacts and machine-specific MCP configuration out of distribution. New customization fixtures must be synthetic. Keep migration evidence consolidated in `docs/migration-audit.md`; removal of v2 does not establish complete migration parity. Generated reports remain local.
